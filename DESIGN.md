# KABİR AZABI — Chapter I: The Sacrificial Gate
Independent adult dark-fantasy top-down action RPG. Turkish UI. A bulky bearded father/barbarian, original design inspired by imposing warriors. No cute models, coins, smiling mobs or children. Target strong desktop PC/Mac; touch tablets too. Detailed adjustable graphics. First chapter 7–8 minutes for a competent player. Beginning and pre-boss checkpoint only; no loot/gold death penalty. Reliable dodge/block, clear telegraphs, readable darkness, death cause.

## Shared classic-script contract (no ES modules)
Global `window.BABA = window.BABA || {}`. Existing global THREE r170 from vendor (`vendor/three.js`, `vendor/gltf-loader.js`). Script order (index.html; sw.js FILES and every `?v=` must match): materials.js, world.js, motion.js, models.js, assets/characters/characters.js, assets/characters/authored-clips.js, authored-motion.js, authored-models.js, combat.js, narration.js, music.js, audio.js, telegraphs.js, effects.js, hud.js, lighting.js, post.js, app.js. ### Loading and shader warm-up
`BABA.Models.prepare({textureScale, maxTexture})` decodes the embedded glTF characters (Düşük: textureScale .5; touch: maxTexture 1024) before `boot()`. Boot builds world, game, effects, post and lighting, then `warmShaders()` starts every program in batches (`renderer.compile(batch, camera, scene)`, KHR_parallel_shader_compile, one painted frame between batches), uploads textures a few per frame and draws one frame before `#loading` hides. Effects and telegraphs keep hidden, never-disposed copies of their on-demand materials (`Effects.warm()`), `Lighting.prepare(game)` patches the character rim light before compiling, `Post.compile()` starts the post passes, `HUD.prepare()`/`HUD.ready` compile the orb contexts. A quality change calls `warmShaders(true)` behind `#warming`; the frame loop does not draw while programs compile. `renderer.debug.checkShaderErrors` is on only with `?debug`. The HUD portrait is `assets/ui/portrait.webp` (384×384, opaque; `?portrait` renders it live with the same camera (slight head tilt), key/fill/rim spot lights, olive skin grading, 3× supersampling, vignette and unsharp mask — save the `#hero-portrait` canvas as webp quality .92 to refresh the file after the hero model changes). The hero's face (arched brows, wide-open brown eyes, forehead lines and crow's feet, grey side hair, full salt-and-pepper beard as a hair mass plus strand fringe) is built in `authored-models.js` (`openEyes`, `browHair`, `beardMass`, `fitBeard`; shader defines `KARA_FACE`, `KARA_HAIR`, `KARA_MASS`) and looks the same in the game and in the portrait.

### Coordinates and camera
Ground XZ, Y up. Forward journey toward negative Z. Model yaw 0 faces +Z; atan2(dx,dz) points toward target. Model height hero ~2.35; standard enemies 2.2, boss 3.7. Map width roughly 20, room progression from z=8 to z=-165. Camera follows from (0,13.8,11.4) on desktop (wider on touch screens) looking toward hero y=.7; maintain readable overhead view.

## Desktop resolution, frame limits and graphics quality (29 September 2026)

The default is high quality at native display resolution with MSAA off. Low / medium / high control scene quality independently of resolution and AA. Native drawing-buffer dimensions are the CSS viewport dimensions multiplied by `window.devicePixelRatio`; resize and monitor-density changes reapply the policy. There are no preset DPR or total-pixel caps, only the GPU's maximum supported side length, applied proportionally. The post targets match the renderer drawing buffer exactly. HTML UI stays native-resolution. Low retains its previous settings. Medium preserves the previous two-tier High exactly: 1536 directional shadows, 5 pooled world lights, .85 world particle scale, 500 combat-particle budget, .019 fog, 768 fire/window shadows and 68-second corpse lifetime. Detailed materials remain. High restores the former full High: 2048 directional shadows, 6 pooled world lights, world particle scale 1, 650 combat-particle budget, .02 fog, 1024 fire/window shadows and 90-second corpse lifetime; post AO 12 samples, 5 bloom levels and 8 ability blur taps, with 10 scattering sources. Medium retains AO 10 samples, 4 bloom levels, 6 ability taps and 8 scattering sources. No quality preset changes MSAA, resolution, gameplay or frame limit. All animation and rendering optimizations stay active.

There is no general resolution-multiplier settings row. Above DPR 1.25, "Yüksek çözünürlüklü ekran" offers "Doğal görüntü" and "Daha akıcı". The latter renders each scene dimension at .75 of native (56.25% of the pixels), leaving HTML text and menus sharp. The expandable "Güçlü bilgisayarlar için" section offers MSAA off / 2× / 4×. Supersampling has been removed from rendering, settings and diagnostics. No automatic hardware-performance classification silently enables AA.

Frame submission is uncapped on non-Mac desktops (FRAME_LIMIT=0) and limited to 60 FPS on Macs, independent of graphics preset. All Macs receive the latter cap because the browser does not reliably distinguish MacBooks from desktop Macs. Browser callbacks still follow display refresh and browser scheduling; uncapped submission is not a guaranteed rate. Combat and animation advance using elapsed time, not a fixed amount per displayed frame. Resolution does not adapt to frame rate.

Opt-in diagnostics (`.`; hidden on every boot) report actual presented-frame intervals, CPU simulation/presentation/submission/HUD times, WebGL adapter, draw counts and asynchronous paired GPU scene/post timings. CPU samples are per presented callback; callbacks skipped by the Mac cap are not included in CPU stages. GPU scene includes the renderer's shadow and MSAA resolve work, while post covers AO/bloom/composition. Separate HUD GL contexts and browser screen presentation are excluded. CPU and GPU overlap; their durations must not be added. No timer extension lookup, polling or query allocation occurs with diagnostics disabled. Resolution, quality, view or visibility changes reset histories; GPU disjoint/context changes invalidate samples. A local JSON download is available; no network transmission or browser history is collected.

Authored motion updates native intermediary nodes and mapped bones once in parent-first order instead of calling getWorldQuaternion for every joint (which recursively recomputed ancestors). CPU-only execution of the actual Three/models/animations/game/world/effects/lighting code on Ryzen 9950X reduced ritual-room game/animation average from 1.762 to 0.955 ms, and measured CPU total from 2.363 to 1.519 ms. Texture pixels, PMREM and WebGL submission were excluded; this is not a browser FPS/GPU result. Old/new transforms, chain states and footfall events were equal across seven character types, nineteen movement/attack/death states and 15,911 frames (22,220,848 matrix values; maximum difference zero).

Stored audio, brightness, subtitles and key bindings survive migration. Quality schema 3 maps the previous two-tier v2 High to Medium once, preserving its look; Low is unchanged, legacy Ultra maps to full High, and explicit schema-3 Medium/High survive reload. Original v1 Medium/High names remain Medium/High, with legacy shadow budgets used only as a fallback. Fresh installs default to full High. Display schema 2 preserves schema 1 native/smooth and MSAA choices, omitting the removed supersampling field. Older resolution and forced-AA choices migrate once to native / MSAA off. Subsequent explicit display and AA selections persist. The `.` diagnostics show actual drawing-buffer dimensions, actual MSAA and the active FPS cap.

Render scheduling uses `pacing.js`: the first actual browser timestamp anchors the deadline; each accepted callback advances one deadline, with nearest-vsync rounding and no backlog burst after a long stall. This avoids rejecting an early callback and then skipping an extra deadline on the late callback. Physics, input, hit-stop and audio retain their existing per-callback clocks. World appearance, camera/occlusion rays, lighting, title idle animation and warning positions prepare only a presented frame, with accumulated presentation delta (capped at .1 s). Three handles scene-matrix updates during the scene render; the app no longer performs a duplicate full-scene traversal. HUD liquid orbs use the same presentation clock, with no independent animation callback or extra draw at each vitals tick. Loading can force a one-off draw at final HUD size. These changes preserve display resolution, quality budgets and selected MSAA. Tests use synthetic callback schedules and inert renderers; they do not measure real GPU performance.

Fog scattering precomputes camera-to-source values per frame and uses one equivalent atan2 integral per pixel/source. AO uses RG16F; positive HDR scene and bloom use R11F_G11F_B10F after framebuffer capability probes, falling back to RGBA16F. This preserves HDR range with reduced colour mantissa precision; scene alpha is not read and no effect uses destination-alpha blending. MSAA is opt-in at every quality preset. The selected sample count intersects the colour/depth formats and is verified using an actual framebuffer; the FPS meter reads that result. Colour and DEPTH_COMPONENT24 resolve before AO; FXAA and its full-resolution intermediate/pass are removed. World decals discard zero-alpha texels before lighting; static direct world meshes keep baked matrices, while moving groups remain live.

Pooled direct lights skip shadow/BRDF work only where their contribution is zero; the skin scattering and clearcoat normal exceptions remain. Mipmapped spotlight cookies are sampled outside the varying cull branch to preserve derivatives. Zero-influence world surface fields skip the remaining vertex math.

Combat particle size follows the actual drawing-buffer height, including the selected display mode and any GPU size limit. Both blood decal textures are uploaded during loading. Each dodge afterimage shares one frozen pose/bone texture per source skeleton; separate ghosts and separate source skeletons stay independent.

Historical validation, before the native-resolution policy above: Apple M4 Pro / Edge Metal, 1512×982 CSS viewport, DPR 2. An earlier High build rendered 3024×1964 and averaged 31.4 FPS in the entrance; the then-capped High build rendered 2076×1348 with verified 4× MSAA. Its seven-room combat run reached approximately 60 FPS, including phase two of the boss. After the MSAA shader-domain fixes, the entrance attack/dodge test averaged 59.85 FPS (95th-percentile interval 17.6 ms, one 45.8 ms interval). One later validation run dropped to 40.58 FPS; another Edge renderer was active, but its content was not identified and the user confirmed no other game was running. A fresh, longer phase-two combat repeat then averaged 60.005 FPS over 735 frames, with 17.5 ms at the 95th percentile and no intervals over 25 ms. The transient dip is not attributed to a confirmed cause. Those checks covered the previous three presets, legacy Ultra migration, previous resize cap, real framebuffer sample counts/completeness and resolved AO depth, with no shader/WebGL/console errors. These historical local headless-browser measurements do not validate performance under the new native-resolution defaults and are not guarantees for every display, power mode or background load.

True MSAA exposes extrapolated edge UVs: fractional-power bases in flame, ribbon and rim shaders are bounded; signed squares use multiplication rather than undefined negative-base GLSL pow. The original attack/dodge artifact was reproduced, fixed and checked with a full-resolution GPU scan of scene+bloom for NaN/Infinity (zero invalid pixels).

## Enemy difficulty (29 September 2026, test build)

The parent found the halls too hard and the foes too fond of their special abilities, so the fights were eased and the specials made rarer. Everything lives in `combat.js` (constants `EASE`, `SPECIAL_GAP`, `SPECIAL_W`; the move tables mark specials with `sp: 1`). No wind-up, tell, blockable/must-dodge rule or hit box changed; nothing depends on the graphics preset.

- **Specials** are the moves that are not the foe's plain blows: prisoner charge (rush) and grab; guard delayed cleave (over) and shield shove; cultist blood rite, paired rite and sacrifice rune; stalker leap and shadow step; carrier vial and rotten breath; executioner hook and ground slam (phase two also cyclone and judgement hooks). Plain blows: claw, chain lash, bash, cut, embers, brazier swing, flurry, spurs, spit, and the executioner's sweep, kick, chain lash and charge.
- **Gate**: after a special an enemy owes `SPECIAL_GAP` plain blows (2; the executioner in phase two 1) before it may use another; an allowed special weighs `SPECIAL_W` (.8) of its table weight; a fresh enemy owes one plain blow first (the prisoner may open with its charge). While specials are held back a carrier walks to spit range instead of standing off to throw vials, and spit works at any range under 5.5 m (up close it used to have only the unblockable breath). Cooldowns of single specials: prisoner grab 7 -> 14 s, cultist rite 14 -> 18 s and paired rite 12 -> 16 s, executioner judgement hooks 13 -> 15 s (last stand 9 -> 11 s). His phase-two charge starts at 6 m (was 7.5), so with the specials held back he still has a plain blow at every range.
- **Round 2 (specials still felt constant)**: `SPECIAL_GAP` is now 3 plain blows for everyone (phase two too), `SPECIAL_W` .4; the "never the same move twice" rule no longer forces a special when only one plain blow fits; a special that is the only legal move (hero kiting out of plain range) waits `SPECIAL_HOLD` (1.5 s of chasing) first; plain blows recover in .75 of the rest time, specials 1.2 (`PLAIN_REST`, `SPECIAL_REST`); cooldowns grab 14 -> 18 s, rite 18 -> 22, paired rite 16 -> 20, judgement hooks 15 -> 18 (last stand 11 -> 13); fresh foes owe 2 plain blows; stalker flurry reaches 3.2 m. Special share of picks (bot, 6 foes each, 90 s) 4-44 % -> 1-17 % (worst case boss phase two kiting 44 -> 17); no tell, hit box or damage changed.
- **Ease**: blows landing on the hero unchanged for common foes (they are lightened by the special gate below), executioner x.88, scaled in `hitPlayer` (tables, tell and heavy-hit thresholds keep the old numbers; since the D4 controls x.88 / x.78, see below); executioner hp 2280 -> 2100 and rest between his moves 1.25 -> 1.3 s. The common foes' hp and pace are unchanged.

## Diablo-4 controls (D4CTRL, 29 September 2026)
The parent asked for the real Diablo-IV-on-PC scheme and for the defence to go: no block, no parry, no whiff swings. Space stays the roll.

**Removed**: hero block / parry / guard-break (`player.block`, the hold state, parry window, block cone, guard cost and stagger of the hero, `blockAge`, block/parry rage gain, `RAGE_GAIN.parry`, the `block` binding, the "blok" slot and tooltip, the SHIFT touch button). Enemy shields (guard type) are unchanged: heavy blows still break them. Hero `stagger` is never set any more (the field stays for the whirl/roar code). The move tables still carry `parry: 'deflect'`, `parryStagger`, `guardPressure` on some hazards; they are read by nothing now (left in place so the enemy tables do not change).

**Telegraph meaning** (`unblockable` keeps its name in code, telegraphs.js/combat.js): crimson = severe blow (`unblockable: true`: rites, runes, quakes, grabs, poison; long tells >= .95 s), gold = ordinary blow. Both are avoided the same way (roll through it, or step out); gold is "avoid it if you can, trading is fine", crimson is "you must roll". Tell lead times and hit boxes are unchanged; nothing lands without a tell. The offscreen arrow says KAÇIN (crimson) / DİKKAT (gold).

**Click-target combat** (`steerOrders` in combat.js, pointer picking `updatePointer` in app.js):
- app.js turns the pointer into `input.target` (the enemy whose screen capsule, feet to head, is within ~3 % of the screen height of the cursor; the previous target keeps it a little longer) and `input.pointX/Z` (the floor point under the cursor, ray to y = 0). A mouse press on a `light`/`heavy` binding is `clickLight`/`clickHeavy`, the button held down is `holdLight`/`holdHeavy`; a key press stays `light`/`heavy` (J, K, pad X/Y, on-screen button).
- Order kinds: `attack` (foe, heavy?), `move` (floor point), `stand` (Shift + click: swing toward the cursor without moving). Left click on a foe = attack order; on the ground = move order; right click on a foe = heavy attack order; right click on the ground = nothing. An attack order walks at run speed until the foe's edge is within `ORDER.reach` (2.6 m; heavy 3.0 m), then starts the swing (`swingPlan`, consumed in `beginAttack`; a click swings once, a held button queues the next chain swing like a key press). Holding left over a foe re-targets the foe under the cursor, holding over the ground steers toward the cursor (`ORDER.hold` .8 m stop distance); a killed foe drops the order and the held button picks the next one under the cursor. WASD/stick cancels a one-shot order; with the button held it only moves the hero (the swing still fires when a foe is in reach). A roll cancels a one-shot order. An approach that makes no progress for `ORDER.stuck` (.7 s) is dropped. There is no way to swing at empty air except Shift + click.
- Attack KEY (J/K/pad/on-screen button): `beginAttack` swings only at a living foe in the front cone (see Facing) and returns false (no stamina spent, no animation) otherwise. The on-screen light/heavy buttons set `near`: the nearest foe within 4.4 m in any direction. Pad: right stick + X/Y = stand swing toward the stick; LB (free now) = whirlwind. Touch: a tap on the game (also a short tap inside the stick zone) is a left click at that point (finger held = mouse held), the stick and buttons work as before.
- The swing turns onto the target (`attack.foe`; at contact `attack.face` is re-aimed at it, so gore and limbs fly away from the hero toward the foe). A stand swing has no lunge. Ring: `showTargetRing` puts a slim additive ember ring under the foe the order targets (bright) or the cursor is on (dim); `player.target` is the foe (read-only, for QA).
- Roll direction: keys, else pad stick, else toward the cursor when an order exists, else facing.

CPU-only actual-model/combat tests preserved attack/hit/death events; measured two-foe cut frame 19.24 to 2.76 ms and triple-guard kill frame 19.35 to 3.83 ms. General p99/GC changes varied between runs, so this is evidence for the cold-cut spike only, not an overall FPS guarantee.

`Effects.warm()` reserves 18 damage canvases/textures/sprites, flashes, actor trail geometry/sample vectors and all five hero ghost skeleton/mesh sets. Pool release resets opacity, tint, actor reference and canvas contents. `combat.js` passes `labelTarget` as the actual actor; hits on that same actor within 120 ms show their summed displayed damage once, while different actors stay separate. Separate labels use their real heights for spacing. Actual old/new ghost poses, ribbons and particle attributes match; cold GPU resource allocation is moved out of ordinary hot paths. Damage and combat clocks are unchanged.

Warm-up also covers customDepthMaterial variants using inherited mesh/skin/instance flags. Shadows compile against an empty scene with the same light collection, matching the real shadow pass fog flags. Bone textures and batch matrix/indirect/colour textures join the upload list; version-zero batch indirect textures are explicitly marked dirty. CPU-only vendor program-key checks match actual shadow keys; these checks do not run a GPU compiler.

Diagnostics schema 2 adds nearest-rank p99 and retains 20 worst presented intervals for the whole measurement, independently of the 240-sample rolling window. Each interval stores the preceding presented CPU stages and position/combat context; this association does not establish causation and does not include skipped-callback CPU work. Fixed8/17/34ms threshold counters describe durations, not automatic judgements about stutter on every refresh rate. Measurements reset on view/visibility/size/settings changes and remain off by default.

Build 44's subsequent user report used the same High/4x settings and adapter but a different room (Curuyen Revir). Its last 240-frame mean was 101.91 FPS, CPU submission 6.85 ms, CPU total 9.10 ms and paired GPU total 6.88 ms, with 922 draws and 1.73 million triangles. This is not a controlled before/after comparison. The 48.97-second session retained a 330 ms interval after a 326.2 ms submission during normal walking at x .829, z -53.007; simulation took 2 ms and presentation .2 ms. The existing GPU rolling window does not cover that old spike, and its cause cannot be inferred from the GPU mean.

Build 45 closes a verified warm-up gap: Three's compile() prepares materials but does not upload geometry. The local renderer.initGeometry(object) extension uploads vertex, morph, index and instance buffers through the existing version/disposal caches, in batches of 12 under the loading cover. Index uploads bind the default VAO first and clean it afterwards; skeletons, poses, per-frame update maps and render counters are untouched. Loader collection includes invisible rooms and distinguishes shared geometry from per-object instance attributes. Real vendor-function tests with recorded mock GL calls verify exact bytes, versioned reuse, VAO preservation and disposal. This removes deferred buffer allocation from room entry; it does not prove the cause of the recorded driver stall or precreate every later shader VAO.

Diagnostics schema 3 separates GPU-probe CPU time, main-scene shadow submission, remaining scene submission and post submission. Only the main scene's shadow callback is measured; empty shadow callbacks in post passes stay within post time. Each frame records program/geometry/texture count deltas and shadow/scene/post draw counts; copies travel with the preceding CPU stages in retained worst intervals. These count deltas indicate resource creation, not every upload or cache-key change. GPU pairs are sampled no more often than once per 100 ms, with up to 120 pairs retained; CPU stages and presented intervals still cover every presented frame. Timing-off rendering performs no extra clock reads or GPU queries and restores the original shadow callback. Real browser performance remains a separate check.

Release build 46 includes the off-scene cut cache in the same geometry-upload stage: limbs.warmGeometryObjects() exposes 287 unique cached geometries (14,303,040 bytes across 1,841 attribute/index buffers), without attaching them to the scene or changing their data. ### Grouped static world drawing

On GPUs exposing WEBGL_multi_draw, boot passes `{multiDraw:true}` to `World.build`. Opaque static templates sharing resolved material, room chunk, detail, shadow flags and attribute layout use BatchedMesh; transparent surfaces, decals, flames and moving props keep their original path. Sorting is disabled for opaque sub-draws; each main or shadow camera still culls individual instances. Original batch distance ranges are retained with setVisibleAt. Without the extension, or with the QA-only `?nobatch`, the original InstancedMesh path remains.
